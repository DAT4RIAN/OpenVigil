# OpenVigil 项目改进建议

- 检查日期：2026-09-26
- 保存日期：2026-09-27
- 检查范围：项目文档、代码结构、关键实现与 CI 配置的只读检查。
- 验证边界：本建议未启动服务、未重跑完整测试，不构成完整审计或生产验收。引用的历史验证结果不能视为当前运行状态。

当前项目最值得投入的是：**补齐真实业务链路验收、验证 Agent 实际效果、降低后续维护成本。** 功能框架、权限治理、异步任务和测试体系已经比较完整，建议按以下顺序改进。

## 改进清单

| 优先级             | 改进点                         | 当前依据与建议                                                                                                                                                                                                                                                 |
| ------------------ | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **P0：正式发布前** | **完成真实环境联合验收**       | 仓库报告仍将真实 CARE 制品、受保护生产环境、镜像签名等标为 `UNVERIFIED`。应在隔离环境跑通“数据接入 → 告警 → 诊断 → 人工审批 → 工单 → 现场证据 → 健康复核”，并把验收证据绑定到同一提交和镜像。已有发布门禁应实际执行。                                          |
| **P1**             | **扩展真实前后端 E2E 覆盖**    | 默认 Playwright 配置排除了 `real-cross-layer.spec.ts`；CI 已有单独的真实链路任务，但该文件目前主要覆盖配置轮换与就绪状态。建议进一步覆盖审批、工单完成、权限隔离、断线恢复和重复提交，证明核心业务闭环可用。                                                   |
| **P1**             | **建立真实模型效果评测**       | 已有 LiteLLM 接入、超时处理、证据约束及治理测试。下一步应建立固定风电案例集，对真实模型测量诊断准确性、证据引用正确率、证据不足时的拒答表现、延迟与单次成本，形成模型和提示词变更的回归标准。                                                                  |
| **P1**             | **统一文档与当前代码状态**     | 已确认具体漂移：`ARCHITECTURE.md` 写 CSS 为 13 个模块，实际为 15 个；迁移头写 `0026`，仓库已有 `0028`。`EXECUTION_GOAL.md` 仍指向旧路径和 CARE 14 项任务，进度文件则记录另一轮技术/UI 整改。建议明确唯一活动任务，归档历史状态，并自动检查迁移头等可生成信息。 |
| **P1**             | **让本地部署可重复执行**       | README 的后端启动步骤列出了 API、通用 worker 和 outbox relay，但遗漏了代码与 Kubernetes 配置中已有的 `read-audit-worker`。建议补齐启动说明，提供项目级启动、状态检查、停止脚本，验证迁移、依赖和全部必要 worker。                                              |
| **P2**             | **继续做小范围模块拆分**       | `production-domain-adapter.ts` 超过千行，诊断中心和预测维护页面也接近或超过千行。建议按业务领域拆适配器，把页面的数据查询、操作流程和展示组件分开；以接口保持兼容、降低单次修改影响面为目标。                                                                  |
| **P2**             | **增加用户实际感知的性能指标** | 当前 bundle 门禁限制总字节数和最大分块，但这些不能直接说明首屏或操作速度。建议补充主要页面的首屏加载、交互响应、长列表渲染和 API P95 测量，再根据结果决定是否调整图表、三维组件加载方式。                                                                      |

## 建议实施顺序

第一批先修正文档和启动流程，同时选定一条真实业务闭环作为验收主线。这能先建立可靠基线，随后再推进模型评测、模块拆分和性能优化。
